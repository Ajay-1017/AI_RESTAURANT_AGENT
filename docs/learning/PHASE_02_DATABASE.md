# Phase 2 — PostgreSQL + SQLAlchemy + Alembic

## 1. Goal

Give the application a real, versioned database layer:

- A connection to PostgreSQL through a pooled SQLAlchemy **engine**
- One database **session** per request (`get_db` dependency)
- A `User` model with a UUID primary key and a unique email
- The `users` table created by an **Alembic migration**, not by hand
- `GET /health/ready`, a readiness check that pings the database
- Tests against a real PostgreSQL test database, rolled back after each test

## 2. Why do we need this?

The app code can't guarantee data correctness alone. Two web requests running at the same moment can both decide "this email is free". Only the database can enforce rules across **all** requests: uniqueness, foreign keys, transactions.

Every later phase depends on it:

| Phase | Needs the database for |
|---|---|
| 3 Auth | users, server-side sessions |
| 10 Booking | orders that survive restarts |
| 11 Payment | atomic "booking + payment attempt" writes, idempotency keys |
| 12 Webhooks | "have I already processed event X?" (unique event IDs) |

And the schema will keep changing, so changes must be **versioned and repeatable**. That's what migrations provide.

## 3. Concepts

### 3.1 Engine vs Session vs Connection

```
Engine  (1 per process)    ── owns a POOL of database connections
  └─ Connection (borrowed)  ── one real TCP connection to Postgres
       └─ Session (1 per request) ── "unit of work": tracks your objects,
                                     turns changes into SQL on commit
```

- Opening a Postgres connection costs a TCP handshake, authentication and memory on the server. The **pool** keeps connections open and reuses them.
- `pool_pre_ping=True` checks a pooled connection before using it, so a restarted database doesn't cause "server closed the connection" errors.
- A **Session** is cheap and short-lived. Never share one between requests or threads.

### 3.2 Dependency injection with `yield`

```python
def get_db() -> Iterator[Session]:
    db = SessionLocal()
    try:
        yield db          # FastAPI runs the route here
    finally:
        db.close()        # always runs, even if the route raised an exception
```

A route asks for it with `db: Annotated[Session, Depends(get_db)]`.

- The route doesn't know *where* the session comes from, so tests can swap it with `app.dependency_overrides[get_db] = ...`.
- `close()` returns the connection to the pool. Forget it and the pool runs dry ("QueuePool limit reached").

### 3.3 Transactions

A transaction is a group of changes that **all succeed or all fail** (atomicity), and that other connections can't see until committed.

```python
db.add(booking)
db.add(payment_attempt)
db.commit()      # both rows saved together...
# ...or on error:
db.rollback()    # neither row exists
```

Without this, a crash between two writes leaves a booking with no payment record, or worse, a payment with no booking.

### 3.4 Primary keys: UUID vs integer

| | Auto-increment integer | UUID (our choice) |
|---|---|---|
| Example | `/users/42` | `/users/7f3e...c21a` |
| Guessable? | Yes, try 41, 43... | No |
| Leaks business info? | "We have ~42 users" | No |
| Generated by | Database on insert | Python, before the insert |
| Index size / speed | Smaller / faster | Larger (16 bytes), fine at our scale |

Guessable IDs combined with a missing authorization check is a classic vulnerability (IDOR, Insecure Direct Object Reference). UUIDs don't replace authorization checks (Phase 3), but they remove the easy enumeration.

### 3.5 Unique constraints and indexes

```python
email: Mapped[str] = mapped_column(String(320), unique=True)
```

This creates `CONSTRAINT uq_users_email UNIQUE (email)`. PostgreSQL implements it with a unique **index**, so:

1. **Correctness:** two concurrent registrations with the same email can't both succeed. A Python `if not exists:` check can't guarantee that (race condition).
2. **Speed:** `WHERE email = ?` at login uses the index instead of scanning every row.

`String(320)` is the maximum email length (64-character local part + `@` + 255-character domain).

**Case-insensitivity.** `Ajay@x.com` and `ajay@x.com` must be one account. We lowercase in the model (`@validates("email")`). Alternatives: Postgres `CITEXT` type, or a unique index on `lower(email)`. Both enforce it in the database. They're stronger but add complexity; we can switch later.

### 3.6 Constraint naming convention

Without a convention, Postgres invents names (`users_email_key`). A later migration that needs to drop the constraint has to know that exact name, and it may differ between databases. We set this once on `Base.metadata`:

```python
"uq": "uq_%(table_name)s_%(column_0_name)s"   # → uq_users_email
"pk": "pk_%(table_name)s"                     # → pk_users
```

Set it **before the first migration**. Renaming constraints afterwards needs its own migration.

### 3.7 Timestamps: `TIMESTAMPTZ` and server defaults

- `DateTime(timezone=True)` → PostgreSQL `TIMESTAMPTZ`. It stores an exact instant (as UTC). A plain `TIMESTAMP` is a "wall clock time" with no timezone, which is a source of subtle bugs between servers in different zones.
- `server_default=func.now()` means the **database** fills it in, so the value is correct even for rows inserted outside the app.
- `onupdate=func.now()` means SQLAlchemy sets `updated_at` when it updates the row. (Raw SQL updates bypass this. A database trigger would cover those; that's not needed now.)

### 3.8 Migrations (Alembic)

A migration is a Python file that changes the schema one step:

```python
revision = "0001"
down_revision = None        # previous migration → forms a chain

def upgrade():   op.create_table("users", ...)
def downgrade(): op.drop_table("users")
```

The database remembers where it is in the chain in the `alembic_version` table (one row: `0001`). `alembic upgrade head` runs every migration after that row.

**Autogenerate** compares your models (`Base.metadata`) with the live database and **drafts** a migration. Always review it, because it:
- can't detect renames: it sees "drop column + add column", which **deletes data**;
- misses some changes (certain server defaults, some types);
- knows nothing about data migrations (backfilling values).

**Why not `Base.metadata.create_all()`?** It only creates *missing* tables. It never alters existing ones, keeps no history, and can't be rolled back.

### 3.9 Alembic and `env.py`

`alembic/env.py` is ordinary Python that Alembic runs. We use it to:
1. Read the URL from `settings` instead of `alembic.ini`, so the password stays out of a committed file.
2. `import app.models`, so every model is registered on `Base.metadata`. Otherwise autogenerate thinks your tables should be **dropped**.

### 3.10 SQL injection

```python
# ❌ NEVER: user input becomes part of the SQL text
db.execute(text(f"SELECT * FROM users WHERE email = '{email}'"))
# email = "' OR '1'='1"  → returns every user

# ✅ ORM / bound parameters: value is sent separately from the SQL
db.scalars(select(User).where(User.email == email))
db.execute(text("SELECT * FROM users WHERE email = :e"), {"e": email})
```

### 3.11 Testing against a real database

- **Why not SQLite?** Different types (no native UUID or `TIMESTAMPTZ`), different constraint behaviour. Tests would pass while production fails.
- **Schema via migrations:** the test fixture runs `alembic upgrade head`, so the migration files themselves are tested.
- **Isolation by rollback:** each test runs inside an outer transaction that's never committed. `join_transaction_mode="create_savepoint"` turns the test's own `commit()` into a SAVEPOINT release, so tests use commit/rollback normally and the database is clean afterwards.

## 4. Architecture

```
Request
  │
  ▼
FastAPI route ── db: Annotated[Session, Depends(get_db)]
  │
  ▼
Session (per request) ──► Engine (pool) ──psycopg 3──► PostgreSQL
                                                       ├── users
                                                       └── alembic_version

Schema changes (offline, never at request time):

models/user.py ─► alembic revision --autogenerate ─► 0001_create_users_table.py
                                                      │ (human review)
                                                      ▼
                                             alembic upgrade head ─► PostgreSQL
```

## 6. Code Explanation

### The model (`app/models/user.py`)

```python
id: Mapped[uuid.UUID] = mapped_column(primary_key=True, default=uuid.uuid4)
```
SQLAlchemy 2.0 style: the type annotation `Mapped[uuid.UUID]` decides the column type (native Postgres `UUID`) and nullability (`Mapped[str]` → `NOT NULL`; `Mapped[str | None]` → nullable). `default=uuid.uuid4` (the function, not `uuid.uuid4()`) runs once per new row, in Python.

```python
is_active: Mapped[bool] = mapped_column(default=True, server_default=true())
```
- `default=` is applied by SQLAlchemy when the app inserts.
- `server_default=` is part of the table definition (`DEFAULT true`) and applies to any insert, including raw SQL or a future migration adding the column to existing rows.

### The readiness check (`app/api/health.py`)

```python
try:
    db.execute(text("SELECT 1"))
except SQLAlchemyError:
    logger.warning("...", exc_info=True)
    raise HTTPException(status_code=503, detail="Database unavailable")
```
- `503 Service Unavailable` tells a load balancer "don't send traffic here right now".
- The full error is **logged**, but the client only sees a generic message. Internal errors can reveal hostnames, versions or SQL.

### Alembic URL handling (`alembic/env.py`)

```python
if not config.get_main_option("sqlalchemy.url"):
    config.set_main_option("sqlalchemy.url", settings.database_url.replace("%", "%%"))
```
- *If not already set*: the test suite sets the test DB URL first, and this line respects it.
- `%` → `%%`: Alembic's config is a `ConfigParser`, where `%` means interpolation. A password containing `%` (or a URL-encoded character like `%3D`) would otherwise crash.

### Test isolation (`tests/conftest.py`)

```python
connection = db_engine.connect()
transaction = connection.begin()                    # outer transaction
session = Session(bind=connection, join_transaction_mode="create_savepoint")
yield session
transaction.rollback()                              # undo everything
```

There's also a safety guard: if `TEST_DATABASE_URL == DATABASE_URL`, pytest stops immediately. The migration test downgrades to an empty schema, and you never want that in your dev database.

## 7. Request Flow

`GET /health/ready`:

1. Uvicorn → FastAPI matches the route `ready`.
2. FastAPI sees `Depends(get_db)` and calls `get_db()`, which creates a `Session` and pauses at `yield`.
3. The route runs `db.execute(text("SELECT 1"))`:
   1. The session borrows a connection from the engine's pool (pre-ping checks it is alive).
   2. psycopg sends `SELECT 1` to PostgreSQL, which returns `1`.
4. The route returns `{"status": "ready", "database": "ok"}`, and FastAPI sends a 200 JSON response.
5. FastAPI resumes `get_db()` after the `yield`: `db.close()` returns the connection to the pool.

If PostgreSQL is down at step 3, an `OperationalError` is raised and logged, and the client gets a 503 response.

## 8. Important Decisions

| Decision | Why | Trade-off |
|---|---|---|
| Sync SQLAlchemy | Simpler; `def` routes run in FastAPI's threadpool | Async (Phase 9+) would mean touching data-access code |
| UUID primary key | Not enumerable; one ID for internal and external use | 16-byte indexes; random inserts fragment the index slightly |
| Lowercase email in Python | Simple, readable | Raw SQL could bypass it (CITEXT / functional index would not) |
| Naming convention from day one | Predictable constraint names for future migrations | — |
| Real Postgres for tests | Same behaviour as production | Developer needs a test DB; DB tests skip without one |
| Schema via migrations in tests | Migrations themselves get tested | Slightly slower test start |
| Readiness separate from liveness | DB outage → stop routing traffic, don't restart servers | Two endpoints |
| Dropped the old `new_agent` tables | Clean migration history starting at `0001` (your choice) | `~/Public/new_agent` no longer works against `ai_restaurant_db` |

## 9. Common Mistakes

1. **Editing tables by hand** (`ALTER TABLE` in psql). The migration history no longer matches reality, and the next autogenerate produces nonsense.
2. **Editing a migration that has already been applied elsewhere.** Other databases won't re-run it. Write a **new** migration instead.
3. **Not reviewing autogenerated migrations.** A rename becomes drop + add, and data is lost.
4. **Forgetting to import a new model in `app/models/__init__.py`.** Autogenerate doesn't see it, or proposes dropping its table.
5. **One global Session shared by all requests.** Corrupted state and threading bugs. Use one per request.
6. **Not closing sessions.** The connection pool runs out under load.
7. **Uniqueness checked only in Python.** Race conditions. Let the database enforce it, and handle `IntegrityError`.
8. **String-formatted SQL.** SQL injection.
9. **Naive `TIMESTAMP`.** Timezone bugs.
10. **Running tests against the dev database.** Tests can wipe it (that's why the guard exists).
11. **Two projects sharing one database.** That's exactly the conflict we hit at the start of this phase.

## 10. Testing

**Create the test database once** (your `ajay` role can't create databases, so use the `postgres` admin):
```bash
sudo -u postgres psql -c "CREATE DATABASE ai_restaurant_db_test OWNER ajay;"
```
Add to `backend/.env`, with the same credentials as `DATABASE_URL` but a different database name:
```
TEST_DATABASE_URL=postgresql+psycopg://ajay:<password>@localhost:5432/ai_restaurant_db_test
```

**Run:**
```bash
cd backend
source ../.venv/bin/activate
pytest -v
```
Expected: `12 passed`. Without `TEST_DATABASE_URL`: `7 passed, 5 skipped`.

| Test | Proves |
|---|---|
| `test_ready_returns_ok_when_database_reachable` | readiness works with a real DB |
| `test_ready_returns_503_when_database_down` | outage → 503, no internal details leaked (no DB needed) |
| `test_user_gets_uuid_and_database_defaults` | UUID PK, `is_active` default, tz-aware timestamps |
| `test_email_is_normalized` | emails stored lowercase and trimmed |
| `test_duplicate_email_is_rejected_by_database` | the **database** enforces uniqueness, even with different case |
| `test_migrations_upgrade_and_downgrade` | migration `0001` works in both directions |
| `test_missing_database_url_fails_fast` | app refuses to start without a DB URL |

**Manual checks:**
```bash
alembic current            # → 0001 (head)
alembic history            # → <base> -> 0001 (head), create users table
uvicorn app.main:app --reload
curl http://127.0.0.1:8000/health/ready     # {"status":"ready","database":"ok"}

psql -h localhost -U ajay -d ai_restaurant_db -c '\d users'   # see columns, pk_users, uq_users_email
```

Readiness failure: stop Postgres (`sudo systemctl stop postgresql`), curl `/health/ready` and you get `503`, while `/health` still returns `200`. Then `sudo systemctl start postgresql`.
